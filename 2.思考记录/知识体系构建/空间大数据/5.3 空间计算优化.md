# 空间计算优化

> 空间计算优化是通过数据组织、索引利用、算法改进等手段提升空间大数据处理效率的技术。

## 数据分区优化

### 空间数据分区

**问题**：传统 Hash 分区会破坏空间局部性

**解决方案**：

```
1. 空间网格分区
   - 按固定网格划分
   - 适合均匀分布数据
   - 实现简单

2. 空间填充曲线分区
   - Z-order (Morton) 曲线
   - Hilbert 曲线 (局部性更好)
   - 将二维映射到一维后分区

3. 自适应分区
   - 四叉树分区
   - K-D Tree 分区
   - 根据数据分布自动调整
```

### 分区策略选择

| 策略 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| 网格 | 均匀分布 | 简单 | 数据倾斜 |
| Hilbert | 通用 | 局部性好 | 计算复杂 |
| 四叉树 | 倾斜分布 | 自适应 | 边界问题 |
| H3 | 区域聚合 | 无边界 | 精度固定 |

### 数据倾斜处理

```
问题: 某些分区数据量远大于其他分区

解决方案:
1. 动态再分区: 监控分区大小，自动分裂大分区
2. 复制热点数据: 将热点区域数据复制到多个节点
3. 采样预估: 先采样确定数据分布，再分区
```

## 索引优化

### 索引选择

```
根据查询模式选择索引:

点查询 → R-tree / GeoHash
范围查询 → R-tree / Grid
KNN 查询 → R-tree
空间连接 → R-tree + 批量处理
轨迹查询 → 时空索引 (3D R-tree)
```

### 索引构建优化

```
批量建索引 (Bulk Loading):
- STR (Sort-Tile-Recursive) 算法
- 先排序再自底向上构建
- 比逐条插入快 10-100 倍

并行建索引:
- 每个分区独立建索引
- 合并索引元数据
- Sedona 支持并行 R-tree 构建
```

### 索引缓存

```
多级索引缓存:
1. 内存缓存: 热点区域的索引
2. SSD 缓存: 频繁访问的索引块
3. 分布式缓存: Redis / Alluxio
```

## 查询优化

### 谓词下推

```
将空间过滤条件下推到数据源:

优化前:
  读取全部数据 → 过滤 → 输出
  IO: 100GB

优化后:
  读取时过滤 → 输出
  IO: 1GB (仅读取匹配的数据)

实现:
- Parquet 的空间过滤下推
- 数据源端的空间索引查询
- GeoMesa 的查询下推
```

### 查询重写

```
1. MBR 预过滤
   精确几何计算代价高
   先用 MBR 快速过滤，再精确计算
   
   WHERE ST_Intersects(a.geom, b.geom)
   → WHERE a.mbr && b.mbr AND ST_Intersects(a.geom, b.geom)

2. 空间索引利用
   确保查询条件能利用空间索引
   WHERE ST_DWithin(a.geom, b.geom, 1000)
   → 使用空间索引快速定位候选对象

3. 连接顺序优化
   小表驱动大表
   先过滤再连接
```

### 空间连接优化

```
空间连接是最耗时的操作之一

优化策略:
1. 分区端复制连接 (Broadcast Join)
   - 小数据集广播到所有节点
   - 避免大数据集的 Shuffle
   - 适用: 点与面的连接

2. 分区端重划分连接 (Repartition Join)
   - 两个数据集按相同空间策略分区
   - 同一分区内进行局部连接
   - 适用: 两个大数据集的连接

3. 批量处理优化
   - 批量执行几何计算
   - 利用 SIMD 指令
   - 减少函数调用开销
```

## 算法优化

### 近似计算

```
牺牲精度换取效率:

1. 网格近似
   用网格代替精确几何
   查询网格而非精确对象
   精度取决于网格大小

2. 采样近似
   对大数据集采样后计算
   结果有统计误差
   适用于探索性分析

3. 概率数据结构
   HyperLogLog: 去重计数
   Bloom Filter: 集合成员判断
   Count-Min Sketch: 频率估计
```

### 增量计算

```
避免重复计算:

1. 增量聚合
   新数据到达时更新聚合结果
   而非重新计算全部数据
   
2. 增量索引
   维护索引的增量更新
   避免重建索引

3. 增量空间连接
   缓存之前的连接结果
   仅对新数据执行连接
```

### 内存优化

```
1. 列式内存格式
   Apache Arrow: 零拷贝内存格式
   列式存储减少内存占用
   SIMD 友好的数据布局

2. 内存映射
   mmap 将文件映射到内存
   操作系统管理页面置换
   适合随机访问大文件

3. 堆外内存
   避免 JVM GC 压力
   使用 Unsafe 或 ByteBuffer
   Spark 的堆外内存管理
```

## 分布式计算优化

### 数据本地性

```
将计算调度到数据所在的节点:

优先级:
1. PROCESS_LOCAL: 数据在同一个 JVM
2. NODE_LOCAL: 数据在同一个节点
3. RACK_LOCAL: 数据在同一个机架
4. ANY: 任意节点

Spark 配置:
spark.locality.wait=3s
spark.locality.wait.process=3s
spark.locality.wait.node=3s
```

### Shuffle 优化

```
空间计算中的 Shuffle 开销大:

优化:
1. 减少 Shuffle 数据量
   - 谓词下推
   - 列裁剪
   - 分区内预聚合

2. 优化 Shuffle 方式
   - 空间分区减少跨分区查询
   - 广播小数据集
   - 使用 Map 端预聚合

3. 序列化优化
   - 使用 Kryo 序列化
   - 空间对象的紧凑编码
```

### 资源调优

```
Spark 资源配置:
- executor-memory: 执行器内存
- executor-cores: 执行器核数
- num-executors: 执行器数量
- driver-memory: 驱动器内存

空间计算特点:
- 计算密集: 需要更多 CPU
- 内存密集: 空间索引需要内存
- IO 密集: 大量数据读写

建议:
- CPU:内存比 = 1:4 或 1:3
- 使用 SSD 存储中间数据
- 启用堆外内存
```

## 存储优化

### 文件格式选择

```
分析查询 → Parquet/ORC (列式)
  - 列裁剪
  - 压缩率高
  - 谓词下推

数据交换 → GeoJSON/FlatGeobuf
  - 人类可读 (GeoJSON)
  - 流式读取 (FlatGeobuf)

大规模存储 → COG (Cloud Optimized GeoTIFF)
  - 按需读取
  - HTTP Range 请求
```

### 压缩策略

```
列式存储压缩:
- Snappy: 速度快，压缩率中等
- ZSTD: 压缩率高，速度中等
- LZ4: 速度极快，压缩率低

空间数据特殊压缩:
- 坐标 Delta 编码
- 整数化 + Varint
- 拓扑压缩 (共享边/节点)
```

## 监控与调优

### 性能指标

```
关键指标:
- 吞吐量: 每秒处理的记录数
- 延迟: 单条记录的处理时间
- 资源利用率: CPU/内存/IO/网络
- Shuffle 数据量: 跨节点数据传输量

空间计算特有指标:
- 空间索引命中率
- 空间连接的候选对数量
- 分区数据均衡度
```

### 调优流程

```
1. 基准测试
   - 建立性能基线
   - 识别瓶颈

2. 数据层优化
   - 选择合适的文件格式
   - 优化数据分区
   - 建立合适的空间索引

3. 计算层优化
   - 调整并行度
   - 优化 Shuffle
   - 启用缓存

4. 查询层优化
   - 谓词下推
   - 查询重写
   - 近似计算
```
